# Reading a database from its dbprint print

**Before any live database call, read the print.** A print is the snapshot `dbprint generate` took of a database, committed to a repository — this one or another — beside its `.dbprint.yaml`, in `prints/<connection>/` unless that file's `output` names another directory. It holds DDL, row counts, per-column statistics, relationships and hand-authored notes for the printed tables. Reading it is offline — no connection, no credentials, no database time — and it carries what a live query does not return: how each listed value is spelled, how complete a value list is, and what people wrote about what a column means.

Where no dbprint server is connected, no `.dbprint.yaml` sits at or above the working directory, and neither the user nor the project's instructions point at a print in another repository, there is no print to read — query the database as usual.

A question is a database question whenever its answer lives in the database, however it is phrased and whether or not SQL is involved: does this table exist, is it empty, how many rows does it hold, are there old records this change has to stay compatible with, which column holds this fact, what values does this status take. Each of those is one tool call against the print.

The tools below are the print's MCP surface. Where they are not connected, `dbprint context <table>` renders a table's context in a shell from anywhere at or below the directory holding `.dbprint.yaml`, and `--project <locator>` reads a print kept anywhere else — a local directory, or a git address such as `https://github.com/<owner>/<repo>/blob/<ref>/<path>/`, cloned read-only through the git credentials already set up. An fnmatch pattern such as `'*.accession'` in place of the name renders every match, and `--purpose query` selects what a query is written from. `uvx dbprint context <table>` runs it with nothing installed, and `pip install dbprint` installs it on Python 3.13 or later. The other tools have no shell twin: find a column by searching the output of `dbprint context --all --purpose query` for its name, then read its table through `dbprint context`, which applies the scope, redaction and missing-measurement rules a raw file leaves to its reader. A server that serves several connections and declares no default needs `connection` on every call; the error it returns otherwise lists the configured names.

| Question | Tool |
|---|---|
| Does a table exist, how many rows it holds, whether it is empty | `list_tables` with `detail: true` and a `pattern` (each table's `row_count`, `profiled_at` and freshness) |
| Which table holds a fact | `search_columns` (start here), `list_tables` |
| Columns, types, nullability, DDL | `get_table_context` |
| Enum values, null rates, ranges, cardinality, key detection | `get_table_context` (Cardinality table, where a long value list shows its 5 most frequent values; `purpose: query` lists every published value) |
| What identifies a row | `get_table_context` (`Grain:` — declared keys at any arity, plus a measured search) |
| The filters and de-duplication a correct query needs | `get_table_context` (description + annotations) |
| Foreign keys and join paths, each stating how it was found | `get_table_context` (Relationships; the Joins list under `purpose: query`) |
| Columns found by shape rather than by name — contact data, uuid/email/phone, candidate keys | `search_columns` filters: `sensitivity`, `looks_like`, `candidate_key`, `classification`, `sql_type`, `redacted` |
| Columns found by what their notes say they hold | `search_columns` with `text` (a substring of the column name, its note or its per-value notes) |
| How a phrase in the question is actually spelled in a column | `resolve_value` (every stored spelling of it — a column holding several needs all of them in the predicate — a value whose note defines the phrase, or the nearest listed values) |
| What changed between the last two prints — tables, columns, joins, statistics that moved | `get_diff` (a table counted in `unevaluated_tables` was not compared, so no event on it is not evidence it held still) |
| Whether the print's statistics are stale | `list_tables` with `detail: true` (each table's `freshness`: `live`, `stale` or `dormant`); in a shell, `dbprint check --max-age 7d` (offline; one unit, `Nd`/`Nh`/`Nm`/`Ns`, never `1d12h`; exit 2 = stale, unless a malformed print, a failed table or a failed assertion outranks it with 1, 5 or 6) |
| What a field in the print actually means | `get_reference` (`document: guide` for how to read a json/yaml field), and the `dbprint://<connection>/reading` resource |

**A reply may be one page of several.** A `list_tables` or `search_columns` reply, like every tool's, carries `next_cursor` while more remains: pass it back as `cursor`, with the same arguments, until a reply carries none — a table or column missing from the first page is not missing from the print.

**Go live only for what the print cannot answer:** an exact row (it publishes none — value lists are frequencies, not rows), a live aggregate, anything newer than the table's `profiled_at`, and a table it does not cover (absent from `list_tables`, or listed under `failed_tables`). A table listed with no `row_count` was described from the catalog alone (`catalog_only`): its columns and types are known, its rows were never read, so it is unmeasured, not empty. A table whose context carries an `External:` line keeps its rows in another system, and every query against it reads that system. A question that lies partly outside the print still starts in it — read what it covers, query the rest, and say which part of the answer came from where.

**Before writing SQL, read the table under `purpose: query`.** `get_table_context` with `purpose: query`, or `dbprint context <table> --purpose query` in a shell, returns the DDL, the Joins list, the data dictionary, and the value lists with their counts and coverage — what a predicate is written from. Every other row above lands in the default `profile` purpose, which carries the statistics that describe the data rather than what a query needs. Reach for `resolve_value` where a filter needs a phrase no list renders in full; where the list is already complete, the call costs a turn and adds nothing.

**The print records what the data holds, not what it means.** What a code, a unit, a sentinel date or a default stands for is in the print only where someone annotated it. A table whose context carries `Meanings: not documented here` has no such notes: read what its codes and units stand for from the code that writes the table, and never infer a business rule from a value list alone.

Resources sit alongside the tools and carry what the tools omit: `dbprint://<connection>/reading` (the traps guide), `.../manifest_annotations` (connection-wide facts, which `get_table_context` also carries as its Connection notes), and per-table `.../statistics`, the only place a column's sketch payload is reachable.

**Three things decide whether a number taken from the print is right**, and the number alone shows none of them:

- **Population.** A `statistics.yaml` carrying a `scope` block was not read whole. Read which cause it names: `sample` (a fraction, to bound cost) or `filter` (a row predicate, verbatim) — never both. Every field in the file except `row_count` is measured over `rows_scanned`. Under `sample`, a row count — nulls, a value's count, a true/false split — may be scaled to table grain by multiplying by `row_count / rows_scanned`; under `filter` nothing rescales, because the scanned set was chosen, not drawn. A distinct count (`cardinality`), a ratio, a percentile, a bound, a mean and `sum` never rescale at all. Where `row_count_method` is `approximate`, the ratio is itself an estimate.
- **Inference.** Everything under `inferred` is dbprint's guess, not the catalog's assertion — `candidate_key`, `looks_like`, `looks_like_candidate`, `sensitivity`, `epoch_unit`. A guess a person rejected is left out of every tool's answer; a raw `statistics.yaml` still carries it, with the column's `statistics.annotations.yaml` entry listing it under `rejected` — read it as no fact about the column. Relationships record the same distinction in `detection`: only `detection: declared` comes from the catalog, `inferred` is proposed from naming, `measured` from value containment. A join a person added reaches the Joins list tagged `annotated` — a person's word with nothing measured behind it — and a join a person rejected is left out of it. An absent `sensitivity` is not a statement that a column is safe.
- **Absence.** An absent field has a cause, and the causes are enumerated per field — fetch them with `get_reference` (`spec`, sections 7.2 and 7.3) rather than guessing. Five cases differ: `unmeasured` is the only marker meaning a run attempted a measurement and failed; `disabled` names a measurement configuration switched off for that table, so everything it produces is unknown, never none; `catalog_only` marks an object no query was issued for, so it carries no `row_count` and no measurement on any column; some absences are assertions, not gaps (no `scope` means every row was read, no `null_patterns` block means no column carries a null unless the file's own `unmeasured` or `disabled` names that block, no `redacted` marker means no redaction rule matched); and the rest are forbidden-for-this-classification, readable off `classification` and `sql_type`.

`values_coverage: 1.0` means an exact-match predicate is complete over what was scanned; anything less is a frequent-value sample, and a value's absence from that list is not its absence from the column. A text column whose `looks_like` is `prose` publishes no value list at all — that is a rule, not a truncation.

**Freshness is not automatic.** The print is regenerated by hand (`dbprint generate`), and every field in it — DDL, row counts and relationships included — is as of that run's `profiled_at`, not as of now. Check it before relying on any of them: `list_tables` with `detail: true` and a pattern gives each table's `profiled_at` and its `freshness` verdict against the threshold it was profiled under, which is cheaper than `get_manifest`'s whole index. Schema and statistics go stale at different rates, and neither is marked stale by itself; in a shell, `dbprint check` gives the same verdict, and `dbprint check --max-age` judges every table against the one threshold it is given.
